# V1 — portal v0: assembly report

2026-09-17. Assembles P1 (hardened image), P2 (closed network), P3 (Git channel) and
P4 (SEB verification) according to [jalon-0.md § V1](jalon-0.md). This document says what
has been **run**, what has been **decided**, and what stays open.

## 1. What is running

```
pnpm install
podman compose -f infra/compose.dev.yml up -d      # Forgejo only
sudo infra/net/setup.sh                            # codespace network + nft (already done)
podman build -t codespace/c-dev:4.137.0 images/c-dev
```

Keycloak does not come from `infra/compose.dev.yml`, which only starts Forgejo: the
development identity provider is the classroom Keycloak, started from the monorepo root.

[setup-poste.md](setup-poste.md); without that alias the command must be written
`podman --remote --url unix:///run/podman/podman.sock build …`, otherwise the binary
silently falls back to local rootless mode and builds into another store.

## 2. What the end-to-end test demonstrates

`scripts/e2e.sh` (a wrapper around `scripts/e2e.ts`) is played in full, on a
fresh test bench (`var/e2e/`), with real containers, the real Keycloak and
the real Forgejo. The eight steps of jalon-0 § V1, plus two:

1. **Real OIDC login** as `student`: authorization code, PKCE, `state`,
   `nonce`, token validation by `openid-client`. The identity displayed comes
   from the IdP. No bypass exists (invariant 4).
2. **Start → workbench → websocket.** The page served really is the one
   of the workbench (`vscode-workbench-web-configuration`), and the websocket
   upgrade is checked for real: `101` **and** `Sec-WebSocket-Accept`
   recomputed from the key that was sent. The same upgrade without a cookie gets a
   403: the proxy does not let a socket through that it would refuse over HTTP.
3. **Inside the container**: the template is already in `/work` (Makefile, `hello.c`,
   `.vscode/launch.json` for `webfreak.debug`), `origin` points at
   `http://portal.internal:9418/git/<session>`; `make`, `gdb -batch -ex run`
   without "Operation not permitted", `show disable-randomization` at `on`;
   `git push` → `PushEvent` in the database with the right sha → commit in Forgejo.
4. **`podman kill`** then reload: a new container is started on the
   **same** volume and the file that was written is there.
5. **Grace period elapsed** (shortened to 8 s for the test, see § 4): container
   destroyed, `work/`, `staging.git/` and `shadow.git/` kept, `shadow.git`
   carries a snapshot that contains `hello.c` and **does not contain** the student's
   `.git`.
6. **Portal restart** with an active session: the session stays
   reachable and the container identifier is **the same** — the reconciliation
   recreated nothing.
7. **`/s/<sid>/` without a cookie**: 403, explicit page.
   **7 bis. Teacher role**: `teacher` gets `/teacher/sessions` with the
   session, the last heartbeat, the last push and the Close button; the same
   table is refused (403) to the student.
8. **Exam mode**: `/exam/exam-c/start` refused without a SEB header, accepted with
   `X-Dev-SEB: ok`, cookies `exam_session` and `cs_session` set, exam
   opened from the same workstation, **refused from another address**. And
   the assertion that matters for invariant 5: a request carrying the SEB
   headers but **without** the cookie stays refused — the proxy reads no SEB header.

Cleanup: the script deletes its session containers. The `codespace-anchor`
anchor, Forgejo and Keycloak are never touched.

Four tables, as in the framing document. **The portal login session is not
a fifth one**: it is a signed self-contained token (`auth/session.ts`), in the
format of `seb/examSession.ts`. What it carries — internal identifier, login,
role, expiry — is already known to the browser, and the immediate revocation of a
login is not a v0 requirement. The *codespace* session, on the other hand, really
is a row: it has a container, a volume and a life cycle.

## 4. Decisions

### D-V1-1. The shadow repository, the volume permissions, and what is left to do

This is the trickiest point of V1. Measured on this workstation, not deduced:

- The volume is mounted `:U`. Podman rechowns `work/` to the UID range that
  `--userns=auto` drew (observed: `2147484647` for uid 1000 of the
  container). **The modes are preserved** and the container umask is `022`,
  so files stay at `644` and directories at `755`.
- The portal runs as uid 1000: it therefore **reads** the working tree, and
  `git --git-dir=<vol>/shadow.git --work-tree=<vol>/work add -A && commit`
  works. Verified, and verified by the end-to-end test.
- **But** a `chmod 600` by the student is enough to make a file unreadable to the
  portal: `git add -A` answers `error: open("x"): Permission denied` and exits with
  128, and **the whole snapshot is lost**. Measured:

  ```
  warning: could not open directory 'privdir/': Permission denied
  error: open("prive.c"): Permission denied
  fatal: adding files failed
  ```

  `--ignore-errors` turns the total failure into a **partial** snapshot: that is
  what `sessions/shadow.ts` does, logging every lost path
  (`partial snapshot: paths unreadable by the portal`).

  This is not a solution, it is a mitigation, and it is named as
  such in the code. **The production solution**, to be worked out at milestone 1,
  is one of these two:

  1. A fixed `--uidmap` per session instead of `--userns=auto`. The portal then knows
     the host UID of the container and can set a default ACL
     (`setfacl -R -d -m u:1000:rX`) on `work/`, inherited by the files created
     afterwards. Cost: the portal has to manage the allocation of the UID ranges,
     that is, redo what `--userns=auto` does on its own, and a
     collision of ranges between two sessions would be a regression of
     the isolation. To be written together with its test.
  2. A **root** systemd timer on the host that takes the snapshot, the
     portal merely declaring which volumes are active. Cost: a second
     unit to deploy and to monitor; benefit: root reads everything, whatever
     the mode, and the portal loses a privilege instead of gaining one. This is
     the preferred lead.

  **What has not been done, and must not be**: removing `:U`. Without it
  the student no longer writes into their own volume. The mitigation does not degrade
  the property, it makes it partial and noisy — the log says exactly
  what is missing.

- Measured corollary: uid 1000 cannot **delete** the volume
  afterwards either (the directory belongs to the container's range). Cleaning up
  the test bench therefore goes through a container, which is what `scripts/e2e.ts` does.
  Volume purging is out of scope for v0 anyway.

### D-V1-2. The session identifier is stable for the life of the volume

`sessions/workspace.ts` writes into `work/.git/config` a remote
`origin = http://portal.internal:9418/git/<session>`. That file is written
**before** the first `podman run` — after it, `:U` has given ownership to the
container and the portal can no longer rewrite it (§ D-V1-1, seen from the
writing side).

Accepted consequence: the portal **never** creates a second session row
for a (student, assignment) pair. It revives the one that exists, whatever
its state. "A single live session per pair" (analyse.md D5)
becomes trivially true, and the remote stays valid after a close and
a reopen.

What it costs: the history of past sessions is not kept; the
teacher table shows one row per pair. The submission trail, on the other hand, is
intact — `push_events` keeps everything, timestamped. If session history
becomes necessary (milestone 4), the way out is a separate table of openings,
not an unstable session identifier.

### D-V1-3. The role comes from the realm

The development realm, the only infra file that was modified, gains:

- two realm roles, `student` and `teacher`, assigned to the accounts;
- a `codespace-roles` mapper (`oidc-usermodel-realm-role-mapper`) that puts the
  user's realm roles into the `codespace_roles` claim
  of the identity token — the client's former `defaultClientScopes` left out the
  `roles` scope, so `realm_access` did not appear there;
- a `preferred_username` mapper, because that is the name that names the
  volume directory and the path of the staging repository;
- a third account, `student2`, so that the seed has two students.

`auth/oidc.ts` reads `OIDC_ROLES_CLAIM` (`codespace_roles` by default) and falls back
on `realm_access.roles` for a realm configured differently. The role is
**recomputed at every login** and never read from the database. A test asserts that a
cookie payload modified to grant itself `teacher` is refused.

Verified end to end: `teacher` gets `/teacher/sessions`, `student` gets a
403 on the same URL.

### D-V1-4. The proxy and the `Location` header

`@fastify/http-proxy` 11.6.2 rewrites the `Location` header of responses by
replacing the rewritten prefix with the prefix of the route. With a
**parameterised** prefix (`/s/:sid`) and an empty rewritten prefix, this gives
`"./?folder=/work".replace("", "/s/:sid")` → `"/s/:sid./?folder=/work"`, an
unsubstituted `:sid` that produces a 404 on reload. Diagnosed by
running the test, not by reading the code.

`internalRewriteLocationHeader: false` turns that rewriting off, and
`replyOptions.rewriteHeaders` redoes it correctly: only a `Location` that is
**absolute as a path** gets prefixed with `/s/<sid>`. The normal case does not need
it, code-server serving everything relatively (`serverBasePath: "."`).

### D-V1-5. Where the container is checked to be alive

The proxy checks that the container is running — and restarts it on the same volume
if it has disappeared — on **entry requests** only (`/s/<sid>/`), that is to say
on page load and reload. Resource requests and
websocket frames make do with the address cache.

The trade-off is explicit: a container killed mid-session does not
show up instantly, it shows up on reload — which a
student does anyway when the editor freezes. Paying one `podman inspect`
per resource request would cost dozens of calls per page load
for nothing.

### D-V1-6. No Playwright

The OIDC flow is driven over HTTP, using the Keycloak form. The browser
would only have added the rendering of the workbench, already covered by the
`vscode-workbench-web-configuration` configuration that is served and by a real websocket
upgrade. The rest of the path — cookies, refusals, addresses — is driven
more reliably over HTTP.

A single concession: Keycloak sets its state cookies as `Secure` even in
cleartext, which a browser accepts on `http://localhost` (an origin deemed secure)
and which the standard library would refuse. The script's cookie jar therefore
does what a browser does on localhost, and nothing more. This is written in
the header of `scripts/e2e.ts`.

`podman exec` replaces the code-server terminal, for lack of a browser: same
container, same `student` user, same hardening.

### D-V1-7. Settings relaxed for the test, and only those

- **Grace period**: `SESSION_GRACE_MS` is 600,000 ms (ten minutes) by default; the
  script sets it to 8,000 ms and says so on screen. It is the only production
  setting that the test changes.
- **`TRUST_PROXY`**: **development only**. It makes `request.ip`
  controllable through `X-Forwarded-For`, which is the only way to simulate a
  second workstation without a second workstation. `loadConfig()` **refuses to start** if
  `NODE_ENV=production` and `TRUST_PROXY` is set, and a test asserts it.
- The `simulated` mode of the SEB verification is refused by `loadConfig()` in
  production, on top of the guard in `createSebVerifier` (invariant 8): two
  guards, the first one gives a configuration message.

### D-V1-8. Public repositories in the development forge

The seed creates the repositories with `private: false`. Reason: in lab
mode the staging repository is a **mirror** of the student's target repository, and
`git/staging.ts` reads it through a `git fetch` that carries no token — that is
deliberate, no secret must travel that way. In production, where the forge is
GitHub and the repositories are private, the mirror will have to go through an authenticated
`fetch`: that is an evolution of `git/staging.ts`, noted in § 6.

> **Done since 2026-09-17.** `ensureStagingRepo` now takes an optional
> `authorization` (`src/git/staging.ts`), used by the seeding `git fetch` and
> carried in the process environment through `gitAuthEnv` — never through argv, never on
> disk. `src/sessions/manager.ts` obtains it from `forgeAuthorization` and passes it,
> falling back to an anonymous fetch when the forge has no credential. The
> paragraph above describes the state of V1 on the day it was written.

### D-V1-9. Relative paths resolved from the repository root

`VOLUMES_ROOT`, `SECCOMP_PROFILE` and `DATABASE_PATH` are resolved from the
root of the application (first ancestor carrying a `package.json`), not from the
directory the process was launched in. Without that, `pnpm --filter` and a launch from the
root designated two different files, and the first `podman run` failed
on `opening seccomp profile failed`. The walk up is **searched for** and not
counted, because the compiled module lives in `dist/auth/` and not in
`src/auth/`.
